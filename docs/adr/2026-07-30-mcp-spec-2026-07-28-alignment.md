# Aligning the MCP Server with Specification Revision 2026-07-28

**Date:** 2026-07-30
**Status:** Proposed — no code yet.
**Driving change:** [MCP specification revision `2026-07-28`](https://blog.modelcontextprotocol.io/posts/2026-07-28/), published 2026-07-28. TypeScript SDK v2 packages (`2.0.0`) published 2026-07-27.
**Interacts with:** [2026-05-29 — Postgres Migration Plan](./2026-05-29-postgres-migration-plan.md), whose **Phase 6 (App Runner → Lambda) is not started but carries a deadline** — App Runner is being sunset. That migration reshapes the same HTTP entry point Phase 2 below touches, and it will probably land *first*, because Phase 6 is on a clock and Phase 2 is not. See [Phase 6 gate](#gate-confirm-the-compute-platform-before-building-this) before implementing the shutdown path.

## Context

### What changed in the specification

Revision `2026-07-28` makes the protocol **stateless**. The changes that matter to a server author:

| Change | Detail |
|---|---|
| **Sessions removed** | The `initialize`/`initialized` handshake and the `Mcp-Session-Id` header are gone. Each request self-describes protocol version, client identity and capabilities in a `params._meta` envelope under reserved `io.modelcontextprotocol/*` keys. Servers can sit behind a round-robin load balancer with no shared storage. |
| **Multi round-trip requests (MRTR)** | Replaces the server→client JSON-RPC request channel, which required an open stream. A server needing input mid-call returns `resultType: "input_required"`; the client retries the original call with answers in `inputResponses` and an opaque `requestState` echoed byte-for-byte. |
| **Header-based routing** | `Mcp-Method` and `Mcp-Name` on every modern-enveloped HTTP request, so gateways route and meter without parsing JSON bodies. Validated against the body; a mismatch is `400` + `-32020`. |
| **Cacheable results** | SEP-2549 **requires** `ttlMs` and `cacheScope` on the results of exactly five operations: `tools/list`, `prompts/list`, `resources/list`, `resources/read`, `resources/templates/list`. The SDK always emits them on 2026-era responses, defaulting to `ttlMs: 0` / `cacheScope: 'private'`. *(SDK behaviour, not a SEP-2549 requirement: `CacheableResultMethod` additionally includes `server/discover`, whose result carries the fields at runtime while hiding them at the type level.)* |
| **Change notifications** | `list_changed` and `resources/updated` are delivered only on a `subscriptions/listen` stream the client opened; servers never send unsolicited notifications. |
| **Deprecations** | Roots, sampling and logging — the three features that structurally required a live bidirectional session — plus the legacy HTTP+SSE transport and Dynamic Client Registration (→ Client ID Metadata Documents). Minimum twelve-month window. |
| **Tasks** | Moved out of experimental core into a formal extension; poll-based `tasks/get` / `tasks/update`. |
| **Authorization** | RFC 9207 `iss` validation before redemption, `application_type` at registration, credentials bound to the issuing authorization server. |

### Where this server stands today

The exposure is **unusually small**, for two reasons: we already run stateless, and we use almost none of the deprecated surface.

Four SDK import sites in `src/`, plus two in the untracked `mcp-harness.mjs`:

| Site | Import |
|---|---|
| `src/server.ts:7` | `Server` from `sdk/server/index.js` |
| `src/server.ts:8-13` | `ListToolsRequestSchema`, `CallToolRequestSchema`, `ListResourcesRequestSchema`, `ReadResourceRequestSchema` from `sdk/types.js` |
| `src/index.ts:19` | `StdioServerTransport` from `sdk/server/stdio.js` |
| `src/transports/http.ts:11` | `WebStandardStreamableHTTPServerTransport` from `sdk/server/webStandardStreamableHttp.js` |

What we do **not** use, and therefore need not migrate: sampling, roots, the logging capability, elicitation, tasks, OAuth (we authenticate with a single shared bearer key at `src/transports/http.ts:48-63`), resource subscriptions, and `list_changed` notifications. The whole MRTR redesign — the largest conceptual change in the revision — costs us nothing, because no handler ever asks the client for anything mid-call.

We are also **already stateless**: `src/transports/http.ts:68` constructs the transport with `sessionIdGenerator: undefined` and builds a fresh `Server` per request. The migration guide states that this exact shape *"maps directly onto the default entry"*. The revision's headline change is one we made in advance.

Prerequisites are met: SDK v2 requires Node 20+ and is ESM-first (we require `>=22.16.0`, `"type": "module"`).

### The two migrations are separate

This is the point most likely to be misread, so it is stated plainly. Moving to the v2 SDK packages and speaking the 2026-07-28 protocol are **different decisions**:

> *"Nothing in v2 puts a 2026-07-28 byte on the wire by default: a hand-constructed `Client` / `Server` / `McpServer` keeps speaking the 2025-era protocol it was written for."* — `docs/migration/support-2026-07-28.md`

Phase 1 is a package refactor with **no protocol-era change**. Phase 2 is an explicit opt-in per entry point. Phase 3 is inert until Phase 2 lands. That is the whole justification for the phase split: each can be reviewed, deployed and rolled back on its own, and a Phase 1 regression is not a protocol-era regression.

**"No era change" is not "no behaviour change" — do not overstate this.** The SDK guarantees only that an ordinary v2 `Server` keeps speaking the era it was written for; it does *not* promise byte-identical legacy responses. `upgrade-to-v2.md:1687` carries a section headed **"Wire tightening (every era)"** whose changes apply on the legacy era too. Five of its six items miss us entirely (elicitation content typing, custom 3-arg handler `_meta` passthrough, `specTypeSchemas` narrowing, the sampling `hasTools` discriminant, and inbound `CallToolResult.content` tolerance — none of which we exercise). **One could touch us:**

> *"Inbound frames that fail message-shape validation are not answered."* — v2 routes every inbound frame through typed message guards; a frame matching no JSON-RPC shape is dropped and surfaces only via `onerror`, where v1 would have answered.

The correct Phase 1 assertion is therefore **"no protocol-era change; existing legacy semantics remain compatible"** — verified by the existing test suite plus a harness run — not byte equality. If byte equality ever matters (e.g. a downstream consumer asserting on raw frames), that needs explicit golden-wire tests; we have no such consumer today and are not adding them.

### Why now, and how urgent

Nothing breaks today. But **two different clocks are running, and they must not be conflated** — an earlier draft of this ADR did exactly that and drew too relaxed a conclusion:

| Clock | Length | Governs | Guaranteed through |
|---|---|---|---|
| **SDK v1 maintenance** | *"at least 6 months after v2's release"* (SDK README) — bug fixes and security updates only, on the long-lived `v1.x` branch | **Phase 1** | ~2027-01-27 |
| **Spec feature deprecation** | Minimum twelve months (feature-lifecycle policy, changelog §Governance 1) | roots, sampling, logging, HTTP+SSE — **none of which we use** | ≥ 2027-07-28 |

Both figures are **guaranteed minimums, not announced expiry dates.** Maintenance does not necessarily stop on 2027-01-27 — it simply stops being *committed* after that point, and we have no basis for planning against an extension that may or may not come.

The twelve-month window is the one usually quoted from the announcement, but it governs *features we do not use*. The clock that actually governs **us** is the six-month SDK one, and it is the shorter of the two. **Phase 1 should therefore land inside the committed window — target end of 2026.** The argument is not that something breaks in January; it is that we should not be carrying a known, un-actioned migration into a period when nobody has promised to fix the SDK underneath us. Uncommitted support is precisely what you cannot plan against, which makes this a firm internal target rather than a preference.

Phases 2 and 3 carry no deadline of their own and are driven by value rather than expiry. That is not the same as being free of timing constraints: **Phase 2 collides with a migration that *is* on a clock** — the App Runner sunset and the Lambda move recorded as Phase 6 of the [Postgres Migration Plan](./2026-05-29-postgres-migration-plan.md). The protocol entry-point changes are platform-neutral, while the shutdown work depends on the selected Lambda adapter, so the two migrations must be sequenced deliberately rather than scheduled independently — see the [Phase 6 gate](#gate-confirm-the-compute-platform-before-building-this). The value arguments:

1. **Clients will begin probing.** A 2026-capable client set to `mode: 'auto'` sends `server/discover` first and falls back to `initialize` when it fails. Against us that fallback costs an extra round trip per connection and — see the CORS finding below — can misfire in browsers.
2. **Cache hints are a genuine performance win** (Phase 3), and are only reachable through Phase 2.
3. **Migration cost rises with drift.** Four import sites and one codemod run today; more if we let the v1 line diverge for a year.

## Decision

Align in **three sequenced phases**, mirroring how the [Postgres migration plan](./2026-05-29-postgres-migration-plan.md) decomposed a large change into independently deployable steps. Each phase is separately revertable and separately valuable.

## Phase 1 — Move to the v2 SDK packages (no protocol-era change)

The single `@modelcontextprotocol/sdk` package is split. We take:

| Package | Why |
|---|---|
| `@modelcontextprotocol/server` | `Server`, `WebStandardStreamableHTTPServerTransport`, and later `createMcpHandler` |
| `@modelcontextprotocol/server/stdio` | `StdioServerTransport` — the root barrel deliberately does not export it, so the root entry stays runtime-neutral for browser/Workers bundlers |
| `@modelcontextprotocol/client` (+ `/stdio`) | `mcp-harness.mjs` only |

We do **not** need `@modelcontextprotocol/core` unless we start importing Zod `*Schema` constants; today we import the schemas only to hand them to `setRequestHandler`, and those become method strings (below).

**Execution:**

```bash
npx @modelcontextprotocol/codemod@^2.0.0 v1-to-v2 .   # package root, not ./src — it rewrites package.json too
grep -rn '@mcp-codemod-error' .                        # sites it recognised but could not safely rewrite
npm run check                                          # tsc --noEmit
npm test
```

**On the version range — what it buys and what it does not.** The migration guide prescribes `@latest`; we use `^2.0.0` so the run picks up codemod bug fixes without drifting to a future major. Be clear that this is **deliberately not reproducible**: `^2.0.0` admits future minors, and with Phase 1 targeted at end-2026 the tool that actually runs could be several months newer than this ADR. Accepting current 2.x behaviour at execution time is the intent, not an oversight.

The justification is that a codemod's artifact is **the committed diff, not the command**. It is run once, reviewed as a normal diff, and never re-run — so having the *best* tool at execution time beats being able to replay the invocation, and a hard pin would mean deliberately running a months-old tool with since-fixed bugs. **Record the exact resolved version in the Phase 1 commit message**: that gives auditability (knowing what produced the diff), which is the property actually worth having here — not repeatability.

The codemod rewrites the import paths, updates `package.json`, and mechanically applies the two changes that touch our code:

- **`setRequestHandler` takes method strings, not schema constants.** `setRequestHandler(ListToolsRequestSchema, …)` → `setRequestHandler('tools/list', …)`, and likewise `'tools/call'`, `'resources/list'`, `'resources/read'`. The four `sdk/types.js` imports at `src/server.ts:8-13` disappear.
- **`RequestHandlerExtra` → `ServerContext`**, parameter renamed `extra` → `ctx`, with `extra.sessionId` → `ctx.sessionId`, `extra.authInfo` → `ctx.http?.authInfo`, `extra.requestInfo` → `ctx.http?.req`. We currently destructure none of these, so this should be a no-op for us — worth confirming rather than assuming.

**The decision the codemod cannot make for us**, and our answer: `StreamableHTTPServerTransport` has a Node fork and a web-standard fork. The rule is *"if your handler receives a Node `IncomingMessage`/`ServerResponse`, use `@modelcontextprotocol/node`; if it receives a web-standard `Request` and returns a `Response`, use `@modelcontextprotocol/server`."* We pass `c.req.raw` (a web `Request`) and return the transport's `Response`, so we take **`@modelcontextprotocol/server`**. The codemod defaults to the Node package, so this is a hand-correction to make after the run.

**Critically for our architecture:** the low-level `Server` class survives, and both v2 serving entries accept a factory returning either an `McpServer` **or** a `Server` (`docs/advanced/low-level-server.md:113,160`). Our `createServer()` factory at `src/server.ts:65` and its four hand-written handlers carry over unchanged. **We are not rewriting fourteen tools onto `registerTool`.** That was the main cost risk in this migration and it does not apply.

**Exit criteria:** `npm run check` clean, 28 test files green, `npm run inspector` connects, no `@mcp-codemod-error` markers left, and `mcp-harness.mjs` drives every tool successfully. The assertion Phase 1 is reviewed against is **"still legacy era, semantics unchanged"** — not byte equality (see [above](#the-two-migrations-are-separate)).

## Phase 2 — Serve the 2026-07-28 revision

Two entry-point swaps. Both serve **2025-era and 2026-era clients from the same code**, so there is no flag day and no client coordination.

**HTTP** (`src/transports/http.ts:66-71`) — replace the per-request transport construction with the handler entry:

```ts
const handler = createMcpHandler(createServer);   // default legacy: 'stateless' — serves both eras
app.all('/mcp', (c: Context) => handler.fetch(c.req.raw));
```

**stdio** (`src/index.ts:28`) — replace `server.connect(new StdioServerTransport())` with:

```ts
serveStdio(() => createServer());   // serves both eras unless legacy: 'reject'
```

### Gate: confirm the compute platform before building this

**Everything in the shutdown section below assumes a long-lived `http.Server` we own.** The [Postgres Migration Plan](./2026-05-29-postgres-migration-plan.md) records that App Runner is being sunset and that **Phase 6 (App Runner → Lambda) is not started but is on a deadline**, whereas Phase 2 here deliberately has none. The likely real-world order is therefore **Phase 6 first**. Depending on the Lambda adapter, that migration may remove the HTTP server entirely or retain one with different termination semantics, so it puts the shutdown work at risk before it is written.

Phase 2 is not uniformly at risk, though — it separates cleanly, and only one part is platform-bound:

| Phase 2 component | Under Lambda |
|---|---|
| `createMcpHandler` HTTP entry-point swap | **Platform-neutral.** It enables the 2026 protocol era while preserving a web-standard `fetch` route compatible with the Lambda adapters under consideration. The current Hono app is already Lambda-compatible, so this swap neither enables nor obstructs Phase 6. |
| `serveStdio` entry-point swap | Unaffected — stdio serving is separate from the Lambda HTTP adapter choice. |
| Two CORS allow-list entries | Unaffected — needed on any platform. |
| Listener drain, idle reaping, timers | **Depends on the adapter** — see below. |

So the gate applies to the shutdown work **only**. The entry-point swaps and CORS fix proceed independently because they are part of the protocol alignment, not because they enable Phase 6. Before implementing the shutdown path:

1. **Confirm the active compute platform.** If Phase 6 has landed or is imminent, stop and re-scope: do the entry-point swap and the CORS fix regardless, but decide the shutdown work against the chosen adapter, because the two candidates differ on whether a listener exists at all:
    - **`hono/aws-lambda` `handle(app)`** — translates the Lambda event into a `Request` and returns `(event, context) => Promise<APIGatewayProxyResult>`. **No HTTP server is created**, so there is no listener, nothing to drain, and the whole section below is void.
    - **AWS Lambda Web Adapter** — runs a real HTTP server inside the container and proxies to it, so a listener *does* exist and some of the drain may still apply. Its termination semantics under Lambda's freeze/thaw and shutdown are **not established here** and would need verifying at that point — do not assume they match App Runner's or a plain container's.
2. **If still on App Runner**, verify its termination contract (see the unverified-grace-period note below), then implement the drain below that grace period.
3. **Either way, treat this as a Phase 2 estimate risk**, not just a design detail: the shutdown path is the largest single piece of work in this ADR and it is the piece most likely to be thrown away.

### If a long-lived HTTP server remains, Phase 2 must build a shutdown path

`createMcpHandler` returns `{ fetch, close, notify, bus }` and `serveStdio` returns a closeable `StdioServerHandle` (`serveStdio.ts:375`) — but **there is nothing in this repository to wire them into.** `startHttpServer` (`src/transports/http.ts:76-96`) discards the listener returned by Hono's `serve()`, and a grep for `SIGTERM` / `SIGINT` / `process.on` across `src/` (tests excluded) returns nothing. Today the process is only ever killed. If the selected hosting shape retains a long-lived HTTP server, this is new work, not a one-line hook-up, and it must be scoped into Phase 2 rather than assumed.

Be precise about what `close()` covers. The released typing (`createMcpHandler.ts:218-224`) is narrower than the prose in `docs/serving/http.md`:

> *"Tears down the **modern leg**: aborts in-flight modern exchanges and closes their per-request instances. **Legacy serving is unaffected** — the stateless fallback is per-request by construction and holds nothing between exchanges."*

The uncovered legacy leg is not a leak: its per-request transport/server pair already tears down on `request.signal` abort (`createMcpHandler.ts:331-337`). But it does mean `handler.close()` alone is **not** a graceful drain — nothing actively ends an in-flight legacy exchange. Those requests simply run to completion on their own; the listener's close callback is how we learn they are done, and only forced socket termination would cut them short.

Required in Phase 2:

- Retain the listener from `serve({ fetch, port })` (narrowed to `node:http.Server` — see step 4) and the handler from `createMcpHandler`.
- Add `SIGTERM`/`SIGINT` handlers with the ordering below. **The ordering is load-bearing and the obvious sequence deadlocks**, so it is specified step by step rather than described.
- Give stdio the same treatment via the `StdioServerHandle`.
- Decide a drain timeout so a hung exchange cannot block shutdown indefinitely. It must sit below whatever grace period the platform allows — a drain longer than that is not a graceful drain, it is a hard kill with extra steps. **We cannot yet name that number.** The `Dockerfile` comment establishes that we run on **AWS App Runner** but says nothing about its termination contract, and a search of AWS documentation found no App Runner–specific statement of the signal sent or the grace period before force-kill (the widely-cited 30-second `SIGTERM`→`SIGKILL` default is **ECS**, via `stopTimeout`, and must not be assumed to transfer). Treat the signal and grace period as **unverified**: confirm them against AWS documentation or by observation before choosing a timeout.
- Make the routine **idempotent** — overlapping `SIGTERM`/`SIGINT` must not start a second drain.
- Clear the reap interval and the drain timer in a `finally`, on every exit path including a rejected `handler.close()`.

**The shutdown sequence, in order:**

1. **Initiate** `listener.close()` — stops accepting new connections. **Do not await its callback here.**
2. **`await handler.close()`** — terminates the modern leg, including any open SSE streams.
3. **Then** await the listener's close callback **while calling `listener.closeIdleConnections()` on a short interval** — in-flight legacy requests complete naturally, and the repeated reap collects each connection as it goes idle. The interval is not optional; see "why step 3 must keep reaping" below.
4. **On timeout**, `listener.closeAllConnections()` to force the remainder (`@types/node/http.d.ts:504`, Node ≥18.2 — we require ≥22.16).

**Typing caveat for steps 3–4.** Hono types `serve()` as `ServerType = Server | Http2Server | Http2SecureServer` (`@hono/node-server/dist/types.d.ts:17`), and both `closeIdleConnections` and `closeAllConnections` exist on `http.Server` only — `Http2Server` declares neither, so calling them on the union does not compile. We use Hono's default HTTP/1 server, so retain the listener narrowed to `node:http.Server` (or guard the calls) rather than typing it as `ServerType`.

**The routine must be idempotent.** Overlapping signals are ordinary — an orchestrator's `SIGTERM` followed by an operator's Ctrl-C, or a repeated `SIGTERM` — and a re-entrant shutdown is worse than the second `close()` merely erroring (it does: the second callback receives `ERR_SERVER_NOT_RUNNING`). The real hazard is duplicated drain state — two reap intervals and two timeout timers, one of which can fire `closeAllConnections()` and kill live exchanges while the other still believes it is draining gracefully. Guard the whole routine behind a single latch and have subsequent signals return the in-flight shutdown promise.

**Both timers must be cleared on every exit path**, in a `finally` rather than at each success point. The reap interval and the drain timeout each carry a distinct failure mode: an uncleared `setInterval` holds the event loop open, so the process that just drained cleanly never exits; an uncleared drain timeout can fire `closeAllConnections()` *after* a graceful shutdown already finished, tearing down connections that no longer belong to it. The path most easily missed is **`handler.close()` rejecting** — without `try/finally` around the drain, that exception leaks the interval and the process hangs, which is a worse outcome than the error that caused it. The paths to cover are: listener closed cleanly, `handler.close()` rejected, drain timeout forced, and a repeat signal arriving mid-drain.

**Why step 1 must not await.** `server.close([cb])` stops accepting new connections and closes *idle* keep-alive connections, but it does **not** terminate a connection with an active request or an open response stream; the callback fires only once every remaining connection has ended. An open modern SSE stream is an active response, and only `handler.close()` ends it — so awaiting the listener callback before step 2 waits on a stream nothing has been told to close, and hangs until the orchestrator `SIGKILL`s the process.

**Why step 3 must keep reaping.** `close()` reaps the connections that are idle **at the moment it is called** — it does not keep reaping. A connection that goes idle *afterwards*, which is exactly what a legacy request completing during the drain produces, is left open if the client holds it keep-alive, and the close callback waits on it indefinitely. MCP clients over Streamable HTTP do hold keep-alive connections, so without the interval in step 3 the drain does not merely risk hanging — **it hangs in the ordinary case**, and the step-4 timeout stops being a backstop and becomes the routine exit path.

Both behaviours were verified empirically rather than read off the typings — see the note below on why the typings mislead here. Because the Node 19 change proves this area does move between majors, the scenarios were run on more than one runtime: **v22.16.0 (our `engines` minimum), v24.19.0, and v25.9.0 (current)**. All three agree. These are representative points, not exhaustive coverage — `engines` is `>=22.16.0`, which is unbounded, so Node 23 and every future major remain untested.

| Scenario | `close()` callback | 22.16.0 / 24.19.0 / 25.9.0 |
|---|---|---|
| Connection already idle when `close()` is called | fires immediately — reaped | identical |
| Response still streaming | stays pending — **this is the step-1 deadlock** | identical |
| Response ends during drain, client keep-alive, no further reap | **still pending at 1500 ms** — the step-3 hang | identical |
| Same, with `closeIdleConnections()` after the response ends | fires immediately after the reap | ~401 / ~401 / ~402 ms |
| Same, but client does not keep alive | fires with the response — socket closes | ~201 / ~202 / ~203 ms |
| Second `close()` on an already-closing server | callback receives `ERR_SERVER_NOT_RUNNING` | identical |

Note that rows 3 and 5 differ only in client behaviour, which we do not control — so the reap interval is what makes the drain terminate rather than the client's good manners.

Note also what row 2 does *not* establish. A timed-out observation shows the callback did not fire within the window, not that it never would; it fires as soon as that response ends. And the response is not intrinsically unclosable — **`handler.close()` closes it, which is precisely what step 2 is for.** Row 2 measures the *incorrect* ordering, where the shutdown is blocked awaiting a callback before it has reached the call that would unblock it. The deadlock is in the sequence, not in the stream.

**On the typings.** `@types/node/net.d.ts:560-562` says `close()` *"keeps existing connections"*. That is **correct for `net.Server`**, which has no keep-alive concept — the Node 19 idle-reaping change applies specifically to `http.Server.close()`. The trap is that `http.Server` declares no `close()` override, so it silently inherits the base class's docstring: accurate where it is written, misleading when consulted for the HTTP server we actually run. That inherited comment is how an earlier draft of this ADR got the semantics wrong.

### Finding: our CORS allow-list will silently defeat browser clients

`src/transports/http.ts:33-39` allows `Content-Type`, `Authorization`, `mcp-session-id`, `Last-Event-ID`, `mcp-protocol-version`. The revision adds `Mcp-Method` and `Mcp-Name` on **every** modern-enveloped request. The SDK guide calls this failure mode out directly:

> *"an opaque CORS/preflight `TypeError` during the probe falls back to the legacy era, because deployed 2025 servers commonly have CORS allow-lists that predate the 2026 headers."*

The failure is **silent and degrading, not loud**: a browser client would quietly drop to the 2025 era rather than error, so we would believe Phase 2 had shipped while browser traffic never used it. `Mcp-Method` and `Mcp-Name` must be added to `allowHeaders` **in the same change** as the entry-point swap, and the acceptance test must assert the negotiated era from a browser-shaped (preflighted) request, not only from `node`.

`mcp-session-id` can stay in the list indefinitely — it costs nothing and remains correct for 2025-era clients.

### Decision: keep our own Hono app

`@modelcontextprotocol/hono` offers `createMcpHonoApp()`, which is `new Hono()` pre-armed with JSON body parsing (into `c.get('parsedBody')`) and DNS-rebinding protection. We **keep our own `new Hono()`** and swap only the `/mcp` route, because our app carries a custom CORS block, a timing-safe bearer-key middleware, and an unauthenticated `/health` route that must stay outside the auth middleware — reproducing those on top of the factory is more churn than it saves. Peer requirements are satisfied either way (`hono ^4.11.4`; we are on `^4.12.11`).

Two consequences to handle deliberately:

- **`parsedBody` pass-through is an optimisation we forgo.** `handler.fetch(c.req.raw)` reads the body itself. Confirm during implementation that the single-read path behaves under our middleware stack; if body double-read becomes an issue, adopt the `parsedBody` pattern rather than the whole app factory.
- **DNS-rebinding protection is not armed.** This is *not a regression* — we have no Host/Origin validation today either — but Phase 2 is the natural moment to add `hostHeaderValidationResponse` / `originValidationResponse` from `@modelcontextprotocol/server` in front of the route. Listed under Open Questions rather than decided here, since it depends on the deployment topology.

### What we deliberately do not adopt

- **MRTR / `requestState`** — no handler solicits client input. If elicitation is ever wanted, it is written once in the `inputRequired(...)` style and the SDK's legacy shim serves it to 2025-era clients too. Note the shim does *not* work under stateless legacy HTTP (no return path for server→client requests), so an interactive tool would need stdio or a sessionful legacy wiring — a constraint to remember before promising elicitation.
- **`subscriptions/listen`** — our tool and resource lists are fixed at build time; we send no change notifications.
- **The authorization work** — RFC 9207, CIMD, DCR deprecation all concern OAuth. Our shared-bearer-key scheme is outside that surface. These are SDK-level opt-ins, not era gates, so nothing is forced on us by moving era.
- **Tasks** — unused; the deprecated wire vocabulary stays importable for 2025-era interop we do not need.

**Exit criteria:** a 2025-era client (current `mcp-harness.mjs`) and a 2026-era client (`versionNegotiation: { mode: 'auto' }`) both drive every tool successfully against one deployed endpoint; a preflighted browser-shaped request negotiates `modern`; stdio serves both eras.

## Phase 3 — Advertise cache hints

Once Phase 2 is live, 2026-era responses carry `ttlMs` / `cacheScope` whether or not we configure anything — defaulting to `ttlMs: 0`, `cacheScope: 'private'`, i.e. "do not cache". Configuring real values is a constructor option on the **low-level `Server`** (`packages/server/src/server/server.ts:121`), not just on `McpServer`:

```ts
cacheHints?: Partial<Record<CacheableResultMethod, CacheHint>>
// CacheHint  = { ttlMs?: number; cacheScope?: 'public' | 'private' }
// cacheable  = tools/list | prompts/list | resources/list
//            | resources/templates/list | resources/read | server/discover  (closed list)
```

So the change at `src/server.ts:71-77` is a few lines:

```ts
{
  capabilities: { tools: {}, resources: {} },
  cacheHints: {
    'tools/list':     { ttlMs: 3_600_000, cacheScope: 'public' },
    'resources/list': { ttlMs: 3_600_000, cacheScope: 'public' },
    'resources/read': { ttlMs: 3_600_000, cacheScope: 'public' },
  },
}
```

**Why `public` is safe here.** `cacheScope: 'public'` permits shared caches, which is only correct when the result does not vary by caller. Ours does not: the `tools/list` payload at `src/server.ts:80-176` is assembled from module-level constants, and `ResourceLoader` (`src/resources/resource-loader.ts`) reads a manifest generated at build time (`npm run generate-manifest`). **Neither can change without a redeploy**, which is also what justifies a long TTL. This reasoning is the thing to re-check if tools ever become caller-dependent — e.g. if the duties tools' availability (`src/server.ts:49`, disabled when the Aurora env vars are absent) were ever made per-request rather than per-process, `tools/list` would vary and `public` would become wrong.

**Why it is worth doing.** Our `tools/list` is a large payload — fourteen tools with full descriptions and JSON Schemas. Because we are stateless, a client that opens a fresh connection per interaction re-lists every time. The size of the win therefore depends on client behaviour: a long-lived Claude Desktop session lists once and gains nothing, whereas a chatbot backend constructing a fresh MCP client per user turn pays the full listing on every turn and gains the most. **We should measure the actual re-list rate against the deployed endpoint before claiming a figure** — the mechanism is certain, the magnitude is not.

**Risk is close to nil.** Hints are emitted only to 2026-era clients; 2025-era responses are byte-for-byte unchanged. Invalid values throw a `RangeError` at construction, so a bad TTL fails at startup rather than silently on the wire. Resolution is most-specific-author-first — handler-returned fields, then a per-registration `cacheHint`, then these server-level hints, then the conservative defaults — so a future handler can override per result without touching this config.

**Sequencing note:** this config is inert before Phase 2 and can be landed early as a no-op, but it should be reviewed *after* Phase 2 so the review can actually observe the fields on the wire.

## Consequences

- **The bulk of the *protocol revision* costs us nothing.** Statelessness we had already; sampling, roots, logging, tasks, elicitation and OAuth we do not use. Across the whole three-phase alignment, the non-shutdown work is one codemod run, one hand-correction, two entry-point swaps, two CORS allow-list entries, and a cache-hints block.
- **But Phase 2 is not a one-line change, and should not be estimated as one.** The largest single piece of work in this ADR is the graceful-shutdown path, which the revision did not require so much as *expose*: signal handling with a defined four-step ordering, an idle-reap interval, a drain timeout, an idempotency latch, `finally`-based timer cleanup, and tests for a routine whose failure modes are a hung process and a premature connection kill. Budget Phase 2 accordingly — the entry-point swaps are the small part.
- **And that largest piece may never be built.** It is specific to a persistent `http.Server` under App Runner, a platform already scheduled for sunset, while the Lambda migration carries a deadline this ADR's phases do not. A native Hono Lambda adapter would remove the listener; Lambda Web Adapter would retain one, although its termination semantics may require a different design. The honest expected value of the shutdown work is therefore conditional — see the [Phase 6 gate](#gate-confirm-the-compute-platform-before-building-this). Its analysis is still worth having: the ordering and the `close()` semantics behind it apply to any long-lived Node server we run, here or elsewhere.
- **One endpoint serves both eras** for as long as the SDK supports the 2025 era, so no client is asked to move in step with us.
- **The low-level `Server` architecture is preserved** — no rewrite onto `registerTool`, and `src/server.ts` keeps its shape.
- **`src/test/transports/http.test.ts` needs reworking** in Phase 2: it drives `createHttpApp` through Hono's `app.request()` and `@hono/node-server`, and the `/mcp` route's internals change. The v2 in-process pattern — a `StreamableHTTPClientTransport` whose `fetch` is `handler.fetch` — gives genuinely better coverage than what we have now, since it exercises a real client against the real handler. There is no in-memory 2026-era transport, so era-specific tests must go through `handler.fetch`.
- **`mcp-harness.mjs` (currently untracked) needs the client-side migration too**, and becomes the natural place to exercise both eras via `versionNegotiation`. Worth committing as part of Phase 1 rather than leaving it out of tree.
- **Phase 2 *may* acquire a graceful-shutdown path we do not have today** — a genuine improvement surfaced by this work, and scope that would otherwise have been missed, but conditional: whether it is built, and in what form, depends on the compute platform and Lambda adapter in play at the time (see the [Phase 6 gate](#gate-confirm-the-compute-platform-before-building-this)).
- **Two clocks, only one of which binds us.** The spec's twelve-month deprecation window covers roots, sampling, logging and HTTP+SSE — none of which we use, so it constrains only what we might build on later. The binding constraint is the **six-month SDK v1 maintenance commitment** (guaranteed through ~2027-01-27, uncommitted thereafter), which is why Phase 1 carries a target date and Phases 2–3 do not.
- **We take on a second protocol era to reason about.** Handler behaviour is era-independent, but bug reports now need the negotiated era attached, and the era-mismatch failure modes (`-32020` header mismatch, `-32022` unsupported version) are new vocabulary for whoever debugs the service.

## Open questions

None of these blocks Phase 1.

- **Production's exact Node patch version is unpinned.** `Dockerfile` (tracked in this repo, and the source of truth — not `../infra/`, which is CDK) builds `FROM node:22-alpine` in both stages. That fixes the **major** at 22, matching the minimum we tested at (22.16.0), so the shutdown table describes production's major rather than a guess. But the tag **floats**: it resolves to whatever 22.x is current at image-build time, so the patch version changes silently on every rebuild and must not be transcribed into this ADR — it would be stale by the next build. Phase 2 should instead record the version it actually verified against in its own implementation evidence (PR or test output), and re-run the shutdown scenarios if the base image is ever moved to a different major. Whether to pin the base image more tightly, so a verified shutdown implementation cannot have its runtime changed underneath it without notice, is worth a separate decision — out of scope here.

- **Deployment topology and DNS-rebinding protection.** Whether to arm `hostHeaderValidationResponse` / `originValidationResponse` in Phase 2 depends on what sits in front of the service (ALB, API Gateway, direct). Leaning **arm it** — cheap, and the current absence is an accepted gap rather than a considered decision.
- **Do we know of any browser-based client?** This decides whether the CORS finding is a latent risk or an active one, and therefore whether Phase 2 is urgent or merely scheduled. Needs an answer from Catherine/Matt before Phase 2 is prioritised.
- **Cache TTL values.** One hour is a placeholder chosen to be obviously safe. Since the payload can only change on redeploy, a much longer TTL is defensible; the constraint is how quickly a tool-description fix should reach clients. Leaning **one hour** initially, revisited with real re-list numbers.
- **Should the chatbot UI's MCP client opt into `mode: 'auto'`?** Out of scope for this ADR — it is a client-side change in a different codebase — but the server work is worth little for our own product until the client negotiates the modern era. Worth raising with Matt as a follow-on.
- **`server/discover` cache hint.** `server/discover` is in the cacheable set and would let clients skip the probe on reconnect. Deliberately omitted from the Phase 3 block above until we have observed real negotiation behaviour; adding it later is one line.
- **Ticket reference.** This ADR has no driving ticket. If the work is scheduled, it should get one for traceability, as LMSC-41 does for the in-force dataset.
